## 0.1 Design principles

These guide every decision in the project.

### Separation of concerns

**Rule: one table = one event, written by one role, at one moment in time.**

If two things happen at different times, or are done by different people, they are different tables.

| Production record | Test record | Why separate |
|---|---|---|
| `Rolls` | `RollTestReports` | Operator vs Extruder Test Person · roll exists first, test comes after |
| `ThermoProductions` | `ThermoTestReports` | Thermo Operator vs Thermo Test Person · same |

**Four concrete reasons, not just theory:**

1. **Different permissions.** The operator may write the roll but not the test; the test person the opposite. With separate tables this is one `[Authorize]` attribute per endpoint. In one shared table you would need column-level security, which neither EF Core nor PostgreSQL makes easy.

2. **Different times.** The roll is created at 09:05. The test is written after. In one table every measurement column would have to be nullable, and "has this roll been tested?" becomes "are these nine columns still null?" — fragile and slow.

3. **Different rules for changing.** A production record is written once and never edited. A measurement may need an administrator to correct a typo, with a reason and history. Two lifetimes, two tables.

4. **Room to grow.** If the factory adds a laboratory test later, it is a new table. The `Rolls` table is never touched, so nothing that already works can break.

### The same principle applies to roles

If two jobs are done at different points in the process, they are different **roles** — even when one man does both today. See [section 3](#3-users-and-roles).

A role is one table row and one constant. Adding it later means editing every `[Authorize]` attribute and redeploying. So define it now, and give one person as many roles as he needs.

### Do not over-apply it

Separation is about **responsibility**, not about splitting everything.

The four thickness readings (RS, RM, LM, LS) stay as **four columns**, not four rows in a child table. There are always exactly four, always the same positions, always written together by the same person at the same moment. Splitting them would add a join and a table for no benefit.

Ask: *do these values have different owners, or different timing?* If no, they belong together.

### The same principle elsewhere in this design

| Split | Because |
|---|---|
| `Batches` separate from `Rolls` | Mixing and producing are different events |
| `MaterialIssueTickets` separate from `MaterialInventoryMovements` | A business document vs a stock ledger entry |
| `PackagingConsumptions` header separate from its lines | One event, many materials |
| `Barcodes` its own table | Identity is a concern of its own, shared by three object types |
| `AuditLog` its own table | Written by an interceptor, never by business code |

### One deliberate exception

`ProducedBags` copies colour, product type, plate size and absorbent flag from its roll. This is duplication on purpose: a pallet scan must check four values in **one** comparison instead of five joins, and it must be fast because it happens thousands of times a day.

It is written once at creation and never editable afterwards, so the copy cannot drift. Every other duplicate in the design is removed.

### In the code

The same rule applies above the database:

```
Controller   →  HTTP only. No business rules.
Service      →  business rules. No SQL, no HTTP.
Repository   →  data access only.
Entity       →  the shape of the data.
```

A controller that calculates a loss percentage, or a service that returns an HTTP status, breaks the rule.

## 1. The factory

The factory makes styrofoam plates. It has **three production lines**, one machine each.

```
LINE 1 — Mixer + Extruder          LINE 2 — Thermoforming        LINE 3 — Recycler
raw materials → mix → ROLL    →    roll → plates → BAGS     →    scrap → RECYCLED MATERIAL
                                   bags → PALLET                          ↓
                                                                    back to inventory
```

### The flow in words

1. The **inventory manager** issues raw materials to the extruder against a ticket.
2. The extruder mixes **one big batch** to a recipe. That batch produces **15–17 rolls** in a shift.
3. Each roll is logged: weight, length, plate weight, four thickness readings. A barcode is printed and stuck on the roll.
4. Rolls wait in stock — **sometimes for weeks**. They are used in the order the customer needs, not first-in-first-out.
5. The thermo machine takes **one whole roll** and turns it into plates. Plates are packed into **big bags of exactly 500** — and each big bag holds **two small bags of 250** inside it.
6. Each **big bag** gets its own barcode. The small bags inside are packaging, not tracked separately.
7. Big bags are scanned onto wooden pallets. **15 bags per pallet.** All bags on one pallet must match.
8. Leftover scrap from thermoforming goes to the recycler, which turns it back into **Recycled Material** for the store.
9. At the end of the shift, **all unused raw material goes back to inventory.**

### Products

A product is defined by four things:

| Attribute | Values today |
|---|---|
| Product type | Plate *(meal boxes planned)* |
| Plate size | Big, Small |
| Colour | White, Green, Yellow, Black … |
| Normal or Absorbent | Normal (NOR), Absorbent (ABS) |

The factory writes this as a short code: **`NOR500`**, **`AB500`** — the type plus the 500 plates in a bag.

## 2. Shifts and shift reports

### Shifts

Three shifts, eight hours each. No shift crosses midnight, so the date of a report is never ambiguous.

| Shift | Start | End |
|---|---|---|
| A | 08:00 | 16:00 |
| B | 16:00 | 00:00 |
| C | 00:00 | 08:00 |

**`Shifts`** — Id · Name · StartTime · EndTime · IsActive

### Shift reports

A shift report is **one line, one shift, one date**. Not one report for the whole factory — the paper form is titled *"Daily Production Report for the Forming Department"*, and the extruder keeps its own log.

**`ShiftReports`**

| Column | Notes |
|---|---|
| Id | |
| ProductionLineId (FK) | Extruder / Thermo / Recycler |
| ShiftId (FK) | A / B / C |
| ProductionDate | date only, no time |
| Status | `Open` · `Closed` |
| SupervisorUserId (FK) | who is responsible for this report |
| ProductionStartTime, ProductionEndTime | actual times worked |
| DowntimeHours | |
| ElectricityStartMeter, ElectricityEndMeter | |
| MachineSpeed, FeedDistance, CycleTime | thermo line: cycles/hour, mm, **seconds** |
| Notes | |
| OpenedByUserId, OpenedAt, ClosedByUserId, ClosedAt | |

**Rules**

- Unique on (ProductionLineId, ShiftId, ProductionDate) — a shift cannot be opened twice.
- Production may only be recorded against an **Open** report.
- Electricity consumption is **calculated** (end − start), never stored.
- Actual production hours are **calculated**, never stored.
- **A shift cannot be closed until every material issue ticket for it is closed** — meaning the leftover has been weighed and returned. This is the factory's own rule and it makes the waste figures exact.
- Reopening a closed shift is an administrator action, with a reason, written to the audit log.

**`ShiftWorkers`** — Id · ShiftReportId (FK) · UserId (FK) · RoleInShiftId (FK) · IsTrainee

The paper form lists workers and trainees on separate lines, so `IsTrainee` keeps that distinction.

## 3. Users and roles

Built on **ASP.NET Core Identity**. Passwords are hashed by Identity — never by our own code.

### One person, many roles

The factory has one man doing both the extruder operator's job and the test person's job today, and wants to split them later without changing anything. So roles are **many-to-many**:

```
Users ──< UserRoles >── Roles
```

A single `RoleId` column on `Users` cannot do this. Identity's `AspNetUserRoles` gives it for free.

**`Users`** extends `IdentityUser` with: FullName · **EmployeeNumber** (unique, e.g. `EMP0006`) · IsActive

The factory identifies people by employee number on paper, so it is stored and can be used to log in.

### Roles

There are **two testing stages** in the factory — one at the extruder and one at the thermo — so there are two testing roles, not one.

| Role | Does | Line |
|---|---|---|
| Administrator | Users, master data, recipes, system settings, backups, corrections | — |
| Supervisor | Recipe versions, inventory adjustments, open/close shifts, approve corrections | — |
| Inventory Manager | Receives materials, issues tickets, records returns | Store |
| Extruder Operator | Creates batches and rolls, prints roll barcodes | 1 |
| **Extruder Test Person** | Records **roll test reports** — weight, length, plate weight, four thickness readings | 1 |
| Thermo Operator | Consumes rolls, records forming, creates produced bags | 2 |
| **Thermo Test Person** | Records **thermo test reports** — plate weight after forming, absorbent percentage | 2 |
| **Packaging Operator** | Creates pallets, scans bags onto them, completes pallets, records packaging materials | 2 |
| Recycler Operator | Records scrap and recycled output | 3 |

*(Both test roles were called "Quality Control" in the old documents. That name is wrong — they do not approve or reject anything. They record measurements, and production continues either way.)*

### A role is cheap now and expensive later

**Rule: define a role for every distinct job, even when one person does several of them today.**

A role costs one row in a table and one constant in code. Adding a role *later* means editing `[Authorize]` on every affected endpoint and redeploying — which is exactly the change the factory wants to avoid.

Right now, one man is very likely all four of these:

```
Extruder Operator  +  Extruder Test Person
Thermo Operator    +  Packaging Operator
```

That is fine. He is given all the roles he needs. When the factory hires someone for packaging, the administrator **removes one role from one person and gives it to another**. Nothing is rebuilt, nothing is redeployed.

This is the whole reason roles are many-to-many rather than one role per user.

**The limit of the rule:** a role must correspond to a real job someone could hold. Do not invent roles for jobs the factory does not have — that describes a factory that does not exist and makes the permission screen confusing. Packaging is a real job; someone does it every shift, even if today he is also the thermo operator.

**`Units`** — Id · Name · Symbol · IsActive
kg · piece · bag · pallet · roll

| Unit | Quantity in base unit |
|---|---|
| bag | 25 |
| pallet | 750 |

The storekeeper picks the material, picks the unit, types the number. The system converts to the base unit. **Stock is always held in the base unit only.**

### Product attributes

**`Colors`** — Id · Name · **Code** (single letter for the roll code: W, G, Y, B) · IsActive

**`PlateSizes`** — Id · Name · IsActive · *(Big, Small)*

### Movement types

**`MovementTypes`** — Id · Name · **Direction** (+1 in / −1 out) · IsActive

| Name | Direction |
|---|---|
| Receive | +1 |
| Issue | −1 |
| Return | +1 |
| Production (recycler output) | +1 |
| Adjustment In | +1 |
| Adjustment Out | −1 |
| Packaging Consumption | −1 |

Direction is **data, not code**. The balance is `SUM(Quantity × Direction)`, and `Quantity` is always positive, so a sign error cannot be stored. `Adjustment` is split in two because a stock count that finds less is a different event from one that finds more.

## 5. Recipes

The factory has **four main recipes** and creates variations often — *"the factory is like a startup, he tries new recipes a lot."*

### The four families

| # | Family | Absorbent | Formula |
|---|---|---|---|
| 1 | Normal Except Black | No | GPPS 100% · Talc 1% · Nucleating 1.5–2% · Colouring 1.5–2% |
| 2 | Normal Black | No | GPPS 65% · Recycle 35% · Talc 1% · Nucleating 1.5–2% · Black colouring 2–2.5% |
| 3 | ABS Except Black | Yes | GPPS 100% · Absorbent 3–4% · Colouring 1.5–2% · Antistatic 1.5–3% · Talc 1% |
| 4 | ABS Black | Yes | GPPS 65% · Recycle 35% · Absorbent 3–4% · Colouring 1.5–2% · Antistatic 1.5–3% · Talc 1% |

### How percentages work

The percentages do not add to 100, and that is correct. **GPPS + Recycle is the 100% base**, and everything else is added on top of it — the standard "parts per hundred resin" method.

Confirmed by the factory's own example (Normal Except Black v1.0):

| Material | Target | Min | Max |
|---|---|---|---|
| GPPS | 100 | 100 | 100 |
| Talc | 1 | 1 | 1 |
| Nucleating Agent | 1.8 | 1.5 | 2 |
| Colouring Agent | 1.6 | 1.5 | 2 |

So each ingredient carries a flag saying whether it is base resin or an additive. Base resin rows must total 100.

### Tables

**`RecipeFamilies`** — Id · Name · ProductTypeId (FK) · UsesRecycle · **IsAbsorbent** · Description · IsActive

`IsAbsorbent` is the NOR/ABS distinction. It is needed on every bag for pallet matching, and it must be a flag — never matched on the family's name.

**`RecipeVersions`**

| Column | Notes |
|---|---|
| Id | |
| **RecipeNumber** | the number the factory says out loud — "recipe 8". Unique, never reused. |
| RecipeFamilyId (FK) | |
| VersionNumber | version within the family |
| Status | `Draft` · `Current` · `Archived` |
| CreatedByUserId · CreatedAt · Notes | |

Only **one `Current` version per family**, enforced in the database:

```sql
CREATE UNIQUE INDEX ux_recipe_current
  ON "RecipeVersions" ("RecipeFamilyId") WHERE "Status" = 'Current';
```

The operator picks **"Recipe 8"**. The system knows it is version 3 of Normal Except Black and holds the exact percentages forever.

**`RecipeIngredients`** — Id · RecipeVersionId (FK) · MaterialId (FK) · **IsBaseResin** · TargetPercentage · MinPercentage · MaxPercentage

### Rules

- A `Draft` version can be edited. Once promoted to `Current` it is **frozen forever**.
- Changing a percentage means **copying to a new version**, never editing.
- Because they experiment often, creating a version must be two clicks: *copy recipe 8 → change one number → save as recipe 9*.
- Every roll points at a `RecipeVersion`, never at a family. Years later the exact formula is still there.

## 6. Inventory

### One table, materials only

Rolls, bags and pallets are **not** in the inventory table. Each is a unique object with its own `Status` column, and counting them is a query:

```sql
-- rolls in stock
SELECT COUNT(*) FROM "Rolls" WHERE "Status" = 'Available';
```

Storing them twice would mean two places to update and two numbers that disagree.

**`MaterialInventory`** — **MaterialId (PK/FK)** · CurrentQuantity · LastUpdated

One row per material, quantity in the base unit. `CurrentQuantity` is a **deliberate** cached total of the movements, kept fast for the stock screen. It is written in the same transaction as the movement, never alone, and a nightly job recalculates every balance from the ledger and reports any difference.

**`MaterialInventoryMovements`**

| Column | Notes |
|---|---|
| Id | |
| MaterialId (FK) | |
| MovementTypeId (FK) | direction comes from here |
| Quantity | always positive, in base unit |
| ShiftReportId (FK) | |
| **IssueTicketId** (FK, nullable) | the ticket that caused it |
| **RecyclerProductionId** (FK, nullable) | recycler output |
| **PackagingConsumptionId** (FK, nullable) | packaging use |
| UserId (FK) · MovementDate · Notes | |

Every movement can name **the event that caused it**, so you can go both ways: from a stock change to its reason, and from a recycler report to the stock it created.

### Rules

- Stock may never go negative. Enforced by a database constraint plus a row lock during the transaction, so two tablets cannot both pass the same check.
- Nobody edits a quantity by hand. Every change is a movement.
- Only Supervisor and Administrator can post an adjustment, and it always needs a reason.
- If the balance blocks production because it is wrong, the supervisor fixes it **on the tablet** — not by finding an administrator at a desk.

### Receiving

The inventory manager picks the material, picks the unit (pallet / bag / kg), types the quantity. The system converts and posts a `Receive` movement.

## 7. Material issue and return

**This is the heart of the waste control**, and it is new — none of it was in the old documents.

The reason it exists, in the owner's words: *"the workers are not careful about the material."*

### How it works

```
1.  Inventory manager creates a ticket   →  stock goes DOWN
2.  Worker collects the material            (no signature — the shift identifies who)
3.  Worker mixes and produces
4.  Leftover is WEIGHED and returned     →  stock goes UP
5.  Ticket closes.  Net used = issued − returned
```

**`MaterialIssueTickets`**

| Column | Notes |
|---|---|
| Id · TicketNumber | printed on the ticket |
| ShiftReportId (FK) | |
| **BatchId** (FK, nullable) | which mix it is for — fills the by-recipe reports |
| IssuedByUserId (FK) | the inventory manager |
| Status | `Open` · `Closed` |
| CreatedAt · ClosedAt · Notes | |

**`MaterialIssueTicketLines`** — Id · TicketId (FK) · MaterialId (FK) · **IssuedQuantity** · **ReturnedQuantity** · unique on (TicketId, MaterialId)

`NetUsed = IssuedQuantity − ReturnedQuantity`, calculated.

Both quantities are **weighed**, so the numbers are real.

**The ticket names the batch, not the recipe.** The batch is enough: batch → rolls → recipe. Storing the recipe on the ticket as well would let the two disagree, and the batch is the thing the material physically goes into.

**The batch itself is never weighed on a scale.** Its weight is the sum of the materials issued to it, less what came back. So the loss we can see is *mixer plus extruder together*, as one number.

This is fine, and it is what the factory does. Worth knowing only so nobody later asks why mixer loss and extruder loss cannot be separated: it would need a scale on the mixed batch, which the factory does not have and does not need.

### The waste control report

This is what the factory actually wants. All the numbers already exist:

```
BATCH 47 — shift A, 2 Aug
Rolls produced:  16   ·   recipes used:  8 (Normal Except Black)

  Materials in (net)     520.0 kg
  Rolls produced out     495.5 kg     (sum of measured roll weights)
  ─────────────────────────────────
  Lost at the extruder    24.5 kg   =  4.7%

  Additive check:
    Talc      5.4 kg  =  1.04% of resin   (recipe says 1%)      ok
    Nucleating 11.8 kg = 2.27% of resin   (recipe says 1.5–2%)  HIGH
```

A shift that used more than the recipe allows becomes visible the next morning. The worker does no extra work — every number comes from something already recorded.

The **"recipes used"** line is read from the rolls the batch produced, not stored on the batch. If a batch turns out to have used two recipes, the report lists both and the additive check is shown per recipe, sharing the materials out by roll weight — with a note that the split is estimated. The kilograms in and out are always exact.

**Rule:** a shift report cannot close while any of its tickets is still `Open`.

## 8. Line 1 — Mixer and extruder

### The batch

One mix produces many rolls, so **the batch is the smallest unit that knows its materials**.

**`Batches`** — Id · BatchNumber · ShiftReportId (FK) · CreatedByUserId (FK) · StartedAt · FinishedAt · Notes

A batch never crosses a shift, because all material returns to store at shift end.

### Why the batch has no recipe column

It would be natural to put `RecipeVersionId` on the batch. **We deliberately do not**, because it is not yet certain whether one batch always uses one recipe — and if it does not, a required recipe column would force the operator to enter something false.

**Recipe and colour both live on the roll**, where they are certain:

```
Batch          →  materials issued, rolls produced        (no recipe, no colour)
Roll           →  which batch  +  which recipe  +  which colour
```

This is known to be safe:

- **Colour definitely changes inside a batch.** The base mix is bulk; the colouring agent is fed separately at the extruder, so the operator switches colour without stopping.
- **Recipe may also change** — not yet confirmed.

The design works either way, and nothing has to be rebuilt when the answer arrives:

| If one batch = one recipe | If one batch = several recipes |
|---|---|
| Every roll in the batch shows the same recipe | Rolls show different recipes |
| Consumption by recipe is **exact** | Consumption by recipe is **shared out by roll weight** — and the report says so |

Either way the roll never lies about its own recipe, and the batch never lies about its own materials. Only the *sharing out* between recipes is affected.

> **To confirm with the factory:** when they mix, do they prepare the base material for **one recipe at a time**, or keep feeding the mixer while the machine runs and change the mixture as they go?
>
> If it is one recipe at a time, a nullable `RecipeVersionId` can be added to `Batches` later — one column, no rebuild — and the by-recipe report becomes exact.

### Rolls

**`Rolls`**

| Column | Notes |
|---|---|
| Id | |
| **DailySerial** | resets to 1 every day |
| **RollCode** | `01WN180726A` — see below |
| Barcode | |
| **BatchId** (FK) | → recipe, → materials |
| ColorId (FK) | chosen per roll |
| ShiftReportId (FK) | extruder line's report |
| ProducedByUserId (FK) | |
| ProducedAt | **full timestamp** — the owner asked for hour and minute |
| Status | `Needs Test` · `Available` · `In Thermo` · `Processed` · `Scrapped` |
| Notes | |

**Roll status flow**

```
produced at the extruder        →  Needs Test
extruder test person saves the measurements  →  Available
thermo operator scans it and starts          →  In Thermo
thermo run finishes                          →  Processed
```

A roll may **only enter the thermo line when its status is `Available`** — that is, only after it has been measured. The thermo operator scans the barcode; if the roll still says `Needs Test`, the system refuses and tells him why.

This is **not** quality approval. The measurements are never compared against limits and a roll is never rejected for bad numbers. The rule only makes sure the measurement was *taken* before the roll is used, because once it is formed into plates the roll no longer exists to measure.

**Roll code** — from a real bag label, `13BAbs240526B`:

```
13   B    Abs   24 05 26   B
│    │    │     │  │  │     └── Shift the roll was made in
│    │    │     │  │  └──────── Year
│    │    │     │  └─────────── Month
│    │    │     └────────────── Day
│    │    └──────────────────── Recipe family  (N = Normal, Abs = Absorbent)
│    └───────────────────────── Colour letter  (W White, G Green, Y Yellow, B Black)
└────────────────────────────── Daily serial — starts at 1 each day, resets next day
```

**Date order is DDMMYY** — day, month, year. Confirmed by the factory.

So `13BAbs240526B` is roll 13 of **24 May 2026**, black, absorbent, shift B. The label on the bag made from it is dated **21 July 2026** — the roll sat in stock for about two months, which matches everything else known about how rolls are used.

Generated by the system, never typed. Unique.

The family part is not a fixed length — `N` is one letter, `Abs` is three. The generator builds the code from the family's own code column, so a future family of any length works without changing anything.

**Status:** a roll becomes `Available` the moment it is produced. **Quality never blocks it.** Rolls are chosen by customer demand, not in order, and may sit in stock for weeks.

### Roll test report

Recorded **once**, as the roll leaves the extruder, by the **Extruder Test Person** — which today is the same man as the operator, holding both roles.

**`RollTestReports`**

| Column | Notes |
|---|---|
| Id · RollId (FK, unique) | |
| Weight | kg |
| Length | |
| **PlateWeight** | from a **sample plate** made from this roll, grams |
| **ThicknessRS, ThicknessRM, ThicknessLM, ThicknessLS** | four readings across the roll |
| AverageThickness | **calculated**, mean of the four |
| TestedByUserId · TestedAt · Notes | |

Named by position, not `Thickness1..4`, because that is what the Roll Log app shows and what the man reads off the gauge.

**The "out time" is `Rolls.ProducedAt`, not a separate field.** The Roll Log app has an *Out Time* box because it has no clock of its own. In the new system the moment the roll leaves the extruder *is* the moment it is created, so it is stored once, as a full timestamp, on the roll. The screen still shows it as "out time" to the operator, and he can correct it if he logs the roll a few minutes late.

**Validation matters here.** The real Roll Log export contains a roll with weight `350` — the operator copied the length into the weight box. A range check (*roll weight 50–150 kg*) would have caught it while he was still standing at the machine. On paper it is wrong forever.

**Relationship:** a roll may have **no** test report yet — `1 → 0..1`, a nullable unique foreign key. A required 1:1 would make it impossible to save a roll before its measurements exist.

## 9. Line 2 — Thermoforming

One roll goes in whole. A roll is never split.

### The production record — the *event*

**`ThermoProductions`** — Id · **RollId** (FK, unique) · ShiftReportId (FK) · OperatorUserId (FK) · StartedAt · FinishedAt · Notes

The operator scans the roll barcode to start. If the roll is not `Available` the system refuses. He never types the roll number, recipe, colour or product — all inherited from the roll.

**Why this table exists when the roll already has a status.** A roll made on 18 July by Ali may be used on 2 August by Omar. The roll's own columns already hold *18 July, shift A, Ali* — that is its birth at the extruder. The thermo facts — *2 August, shift B, Omar, in at 09:10, out at 10:00* — are a **different event** and have nowhere else to live.

Status cannot carry them. `Processed` says the roll was used; it does not say when, by whom, or in which shift. And when a status changes, the previous value is gone — status is the present, never the history.

The alternative would be adding `ThermoShiftId`, `ThermoOperatorId`, `ThermoStartedAt` and `ThermoFinishedAt` to `Rolls`, putting two separate events in one row. That is exactly what [section 0.1](#01-design-principles) forbids.

This record is also the parent of the test report and of every bag the run produced.

**Relationship:** `Roll 1 → 0..1 ThermoProduction`. Most rolls are processed; a scrapped roll never is.

### The test report — the *measurements*

Recorded by the **Thermo Test Person** after the run, from the factory's own form.

**`ThermoTestReports`**

| Column | Arabic on the form | Notes |
|---|---|---|
| Id · ThermoProductionId (FK, unique) | | |
| **TotalTimeMinutes** | الزمن الكلي | |
| **PlateSizeId** (FK) | حجم الصنف | Big / Small |
| **BagCount** | عدد الأكياس المنتجة من الرول | |
| **PlateCount** | عدد الصحون المنتجة من الرول | |
| **PlateWeight** | وزن الصحن المنتج، غرام | measured again after forming |
| **AbsorbentPercentage** | نسبة الإمتصاص للصحن المنتج % | ABS recipes only; `0` for Normal |
| **BagWeight** | وزن الكيس المنتج الواحد، كغم | |
| TestedByUserId · TestedAt · Notes | | |

**No duplication.** Roll weight, roll length and roll thickness appear on the paper form but are **not** stored here — they already exist in `RollTestReports`. The screen shows them read-only, in the same position the operator is used to, pulled from the roll.

`PlateCount = BagCount × 500`. The real form confirms it on every roll: 14→7000, 12→6000, 9→4500, 12→6000, 14→7000.

Plate weight is measured **twice** in the factory — once from a sample plate at the extruder, once here after forming. Both are kept. A gap between them points at a forming problem.

**Relationship:** `ThermoProduction 1 → 0..1 ThermoTestReport`.

### When the bags are created

The bag count lives in the test report, so **saving the test report is what creates the produced bags** and prints their barcodes.

That matches the factory: the bags are counted at the end of the run, so the number does not exist until then.

One thing to watch after go-live: the packaging operator cannot start building a pallet until the test person has saved his form. Today one man holds both roles, so it costs nothing. If the factory later splits the jobs and packaging finds itself waiting, the fix is small — move `BagCount` to `ThermoProductions` so the operator enters it himself. Nothing else in the design changes.

### Produced bags

**The packed unit is the big bag: 500 plates, made of two small bags of 250 inside it.**

```
1 big bag  =  500 plates  =  2 small bags × 250 plates
```

The big bag is what carries a barcode, what goes on a pallet, and what the reports count. The small bags are **packaging material**, consumed two per big bag — they are not separate tracked objects and do not get barcodes.

Created automatically when the production is saved. One row per big bag, one barcode per big bag.

**`ProducedBags`**

| Column | Notes |
|---|---|
| Id · Barcode | |
| ThermoProductionId (FK) | → roll → batch → recipe |
| **ColorId · ProductTypeId · PlateSizeId · IsAbsorbent** | copied at creation — the four pallet-matching attributes |
| Weight · PlateCount | |
| Status | `Available` · `Assigned` · `Defective` |
| CreatedAt · Notes | |

The four attributes are copied deliberately so a pallet scan is one fast comparison, not five table joins.

**Defective bags** are not packaged. They go to the recycler, so their weight becomes part of the shift's scrap. This makes *plates produced* and *plates packed* two different numbers — both are shown, so the difference is never mistaken for a packing error.

## 10. Pallets and packaging

### Why every bag needs a barcode

The factory asked for it, and the real form proves it is necessary.

On 2 July: one green roll made 14 bags; four yellow rolls made 12 + 9 + 12 + 14 = 47 bags. The pallets were 14 green, then 15 + 15 + 15 + 2 yellow.

15 does not divide 12, 9 or 14 — so **pallet 1 holds bags from roll 10 and roll 9**, and pallet 2 holds bags from roll 9 and roll 4. Without a barcode on each bag, nothing can say which roll a bag came from.

### Pallets

**`WoodenPallets`**

| Column | Notes |
|---|---|
| Id · PalletNumber · Barcode | |
| ShiftReportId (FK) | |
| **ColorId · ProductTypeId · PlateSizeId · IsAbsorbent** | **all NULL until the first bag is scanned** |
| Status | `Empty` · `Opened` · `Completed` · `Shipped` |
| CreatedByUserId · CreatedAt · CompletedAt · Notes | |

**Bag count and plate count are NOT stored.** They are `COUNT()` and `SUM()` over the assignments — a pallet holds 15 rows, so counting is instant.

### The rule the factory gave

> *"When the pallet is empty, the pallet will take the first scanned bag's characteristics."*

```
Empty pallet          →  colour, size, type, product all NULL
First bag scanned     →  those four are SET from the bag  →  status becomes Opened
Every later bag       →  must MATCH all four, or it is rejected
15 bags reached       →  status becomes Completed
```

**`BagPalletAssignments`** — Id · ProducedBagId (FK, **unique**) · WoodenPalletId (FK) · **AssignedByUserId** (FK) · AssignedAt

The user is recorded. This is the most repeated manual action in the factory and it must be accountable.

The unique index on `ProducedBagId` is what actually stops a bag being put on two pallets — application code alone cannot, because two tablets can scan at the same moment.

**Corrections.** A wrong scan happens. Assignments are never deleted: a supervisor posts a **reversal** with a reason, the bag returns to `Available`, and the history shows both events.

**Capacity** is 15 bags, stored as configuration per product type and plate size — not written into the code — so meal boxes can differ later.

**Partial pallets are normal.** The two unnumbered groups on the paper form (14 bags and 2 bags) are simply `Opened` pallets waiting for more bags. Nothing needs to force them closed.

### Packaging materials

Recorded once at the end of the shift by the **Packaging Operator**. The real form shows **fractional** quantities (small bags 4.14, large bags 6.1) alongside weights — so the factory *does* measure partial use, by weighing.

**`PackagingConsumptions`** — Id · ShiftReportId (FK) · RecordedByUserId (FK) · RecordedAt · Notes

**`PackagingConsumptionLines`** — Id · ConsumptionId (FK) · **MaterialId** (FK) · **Quantity** (decimal) · **Weight** (decimal, nullable) · unique on (ConsumptionId, MaterialId)

The factory records **both a count and a weight**, exactly as the paper form does — `العدد` and `الوزن (كغم)`. Some materials have both, some only one:

| Material | Count | Weight |
|---|---|---|
| Large bags | ✔ | ✔ |
| Small bags | ✔ | ✔ |
| Shrink | ✔ | ✔ |
| Plastic hood | ✔ | ✔ |
| Tape | ✔ | — |
| Wooden pallets | ✔ | — |

**Quantity is the number of individual units, not packs.** A shift that used 61 large bags stores **61**. Quantity stays decimal anyway, because tape and shrink are genuinely part-used — half a roll of tape is `0.5`.

### The weights on the paper form prove the counts

The count column on the 2 July form is wrong — but the **weight column is right**, and it proves what the counts should have been:

```
Large bags:  5.185 kg ÷ 61 bags   =  0.085 kg  =  85 g each   ✓ exact
Small bags:  5.800 kg ÷ 122 bags  =  0.0475 kg =  47.5 g each ✓
```

61 big bags were produced that shift, and 122 small bags is exactly 61 × 2. So the weighed figures agree perfectly with what the system will calculate, while the handwritten counts (`6.1` and `4.142857`) are simply mistakes.

This is good evidence that the calculated counts can be trusted.

### A free packaging waste check

Because both numbers exist, the system can compare them — the same idea as the material waste report.

Add an optional **`UnitWeight`** to `Materials` (85 g for a large bag, 47.5 g for a small one). Then:

```
Expected weight  =  calculated count × unit weight
Actual weight    =  what the operator weighed
Difference       =  bags torn, wasted, or used elsewhere
```

Nobody does extra work — the count comes from production, the weight is already recorded on the form today.

One row per material — **never one column per material**. Adding a new packaging material is then a data change, and each line posts its own stock movement directly with no mapping code.

### Three packaging materials the system can count by itself

These do not need to be typed at all, because the system already knows the numbers:

| Material | Used | From |
|---|---|---|
| **Large bags** | 1 per produced bag | `COUNT(ProducedBags)` |
| **Small bags** | **2 per produced bag** | same × 2 |
| **Empty wooden pallets** | 1 per completed pallet | `COUNT(WoodenPallets Completed)` |

So a shift that made 61 bags on 3 pallets used exactly 61 large bags, 122 small bags and 3 pallets. The operator types nothing and the numbers cannot be wrong.

**Tape, shrink and plastic hood** cannot be counted this way — they are used by length and by feel — so those stay as typed shift totals, weighed where the factory weighs them.

**This gives a second free check.** The system's calculated bag usage can be compared against what was actually taken from the store, exactly like the material waste report:

```
Calculated:  61 large bags, 122 small bags
Weighed:      5.185 kg large, 5.8 kg small
```

A gap means bags are being wasted, torn or used elsewhere.

## 11. Line 3 — Recycler

At the end of the shift all scrap is collected and weighed, recycled, and the output weighed again.

**`RecyclerProductions`** — Id · ShiftReportId (FK) · **ScrapWeight** · **RecycledMaterialWeight** · RecordedByUserId · RecordedAt · Notes

`LossPercentage` is **calculated**, not stored: `(Scrap − Recycled) ÷ Scrap`.

Saving the record posts a `Production` movement that increases **Recycled Material** in the store. One material, no split.

### The free accuracy check

The thermo report *calculates* loss per product; the recycler *weighs* the same scrap.

```
Thermo calculated:  171 kg  (445.5 − 30,500 × 9 g)
Recycler weighed:   ??? kg
```

If these differ a lot, either the plate weight is wrong or scrap is going missing. Both numbers already exist — the check is free.

## 12. Barcodes

**v1 barcodes three things: rolls, produced bags, wooden pallets.** Raw material barcodes are explicitly **not** in v1.

**`Barcodes`** — Id · **Value** (unique) · **ObjectType** (`Roll` / `Bag` / `Pallet`) · ObjectId · CreatedAt · IsActive

One table owning every barcode. This gives three things a per-table column cannot: uniqueness across the whole system in one place, a single lookup for "scan anything and find it", and an instant answer when a bag is scanned into a pallet field — *"that is a bag, not a pallet"* instead of a failed search.

### The bag label the factory prints today

From a real label photographed on a bag of black absorbent plates:

| Field | Arabic | Value on that label |
|---|---|---|
| Day | | Tuesday |
| Date | | 21-7-2026 |
| Roll number | رقم الرول | `13BAbs240526B` |
| Product | نوع الطبق | `AB500B` |
| Plates per bag | عدد الأطباق / كيس | 500 |
| Type | | absorbent |
| Shift | الوردية | A |
| Time | الوقت | 15:28 |
| Barcode | | `AB500B` |

Two things this tells us.

**1. The label already carries the roll number.** The factory is doing manual traceability on paper — the bag knows which roll made it. Good: the new system keeps this field, so the label looks familiar.

**2. The current barcode is *not* unique.** It encodes `AB500B` — the **product code**, so every bag of black absorbent 500 has the same barcode. It identifies the *type*, not the *bag*.

That cannot build a pallet. Scanning it would say "this is a black absorbent bag" but never *which* bag, so the system could not stop the same bag going on two pallets, nor know which roll it came from.

**So the new barcode must be unique per bag.** The product code stays printed on the label as text, because that is what people read — but the barcode itself carries the bag's own identity.

The label also confirms the shift on the bag is the **thermo** shift (A), while the shift inside the roll code is the **extruder** shift (B). Two different shifts on one label, which is exactly why `ThermoProductions` exists as its own record.

**Product code format:** `AB500B` = type (`AB` / `NOR`) + plates per bag (`500`) + colour letter (`B` = black). Generated from the bag's own attributes, so it can never disagree with them.

### Format

- **QR code** recommended, since the workers use Android tablets and a camera reads QR at an angle and survives a damaged label better than a linear barcode.
- The label prints the **human-readable code above the barcode** — `01WN180726A` for a roll — so a man can read and type it if the label is torn.
- Barcodes are never reused, even for a scrapped object.
- The printed label keeps every field the factory prints today, plus the unique bag code.

**Reprinting is allowed** for the same object, and every print is logged. A supervisor can see who reprints unusually often.

**Manual entry is allowed but marked.** The audit log distinguishes `Scanned` from `Typed`. Work never stops because of a ruined label, and a report shows typing rates per user — which controls the behaviour better than a ban the workers would have to break.

## 14. What the system cannot do

Stated plainly, so no report promises more than it can deliver.

**1. Per-roll material consumption — impossible.**
One mix makes 15–17 rolls. The system can say exactly what went into **batch 47** and which rolls came out of it, but not how much GPPS went into roll 3. This is physics, not software.
*What you get instead:* full material detail per batch, and every roll names its batch.

**2. Per-roll yield — impossible**, for the same reason. Yield is available per batch and per shift.

**3. Recycled material history — impossible.**
All recycled material goes into one pile. A black roll can say it used Recycled Material, but not which shifts produced it. Fixing this would need the factory to store each shift's recycled output separately — a physical change, not a software one.

**4. Who exactly took the material — not recorded.**
There is no signature at the store. Attribution is by **shift**, which is what the factory asked for.

**5. Warehouse locations — not in v1.** A pallet is "in the factory", not "in row 3, bay 2".

## 15. Security and deployment

### Security

- ASP.NET Core Identity for login. **HTTPS from day one** — tokens and passwords cross factory Wi-Fi, so this is not optional and is cheapest to set up while the tablets are being configured.
- Short access token with a refresh token, so a twelve-hour shift never logs a man out mid-roll, and a deactivated user loses access quickly rather than at token expiry.
- **Tablets belong to machines, not people.** A single login at shift start would attribute twelve hours of work to one man. The fix that fits this factory: **the worker scans his own badge barcode** with the scanner already in his hand, before actions that matter. It costs one scan and makes the audit trail true.

### Audit log

**`AuditLog`** — Id · UserId · **ShiftReportId** · Action · ObjectType · ObjectId · Result (`Success` / `Rejected`) · Details · Timestamp

Written by one EF Core `SaveChanges` interceptor, so nothing is missed. It covers **all** important actions, not only barcode scans — recipe versions, inventory adjustments, shift reopening, assignment reversals.

**Failed actions are logged too.** A rejected bag scan changes no data, but a man scanning wrong bags repeatedly is exactly what a supervisor wants to see.

### Deployment

One Windows Server on the factory network: React frontend, ASP.NET Core API, PostgreSQL. No internet needed to run.

The developer is **two hours away**, so three things are required, not optional:

| | Why |
|---|---|
| **Logging to files from day one** (Serilog) | Without it, a 2am failure can only be diagnosed by telephone |
| **A `/health` endpoint** | Answers "is the server up?" without driving there |
| **Deploy to timestamped folders** | Rollback becomes switching back to the previous folder — one minute over remote desktop, no rebuild |

**Database migrations** are an explicit step in the deployment, with a **backup taken immediately before**. A bad migration then costs minutes instead of a day of production history.

**Backups** go to the server, an external drive, and optionally cloud. A backup stored only on the machine it protects is not a backup. Restores are tested quarterly — a backup nobody has restored is only a hope.
